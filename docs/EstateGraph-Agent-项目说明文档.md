## 01｜项目概述

**一句话定义**：EstateGraph Agent 是一款面向**继承律师 / 家事法务团队**的复杂案件智能分析系统，帮助他们把散落在几十份材料里的人物、资产、证据和法律事实，自动结构化为可核查、可计算、可复用的案件图谱与分析报告。

**核心能力组合**：

- **AI 文档理解**——从 PDF、扫描件、Word、Excel 中抽取人物、身份、时间、亲属关系、资产、金额、权属、债权债务与遗嘱信息；
- **人物关系图谱**——自动识别被继承人及各类继承人，标注关系类型、发生时间、证据来源与可信度；
- **资产图谱**——区分「资产总价值 ≠ 被继承人份额 ≠ 净遗产」，处理共有财产析产、抵押与债务；
- **法律知识检索（RAG）**——检索《民法典》继承编条文、司法解释与权威案例；
- **规则计算引擎**——在确定的法律事实之上，做确定性的法定份额与分割计算（**[已具备]**，复用 HeirArena 规则引擎）。

**产品边界**：EstateGraph Agent **不替代律师的最终判断**。它只做**结构化辅助**——读材料、找关系、理资产、查规则、算数字、发现冲突与缺失；证据采信、争议定性、法律解释与最终专业意见仍由律师负责。系统在证据不足时会**主动弃权（Abstain）**，而不是替律师"猜"一个答案。

**核心目标**：把律师原本需要**数小时到数天**的材料整理、关系梳理与份额估算工作，压缩到**数分钟到数十分钟**，并让每一个结论都能一键反查到原始材料来源。

## 02｜问题背景

复杂继承案件的难点，不在"会不会算"，而在"事实太脏、太多、太容易冲突"。

**痛点一：人物关系混乱。** 现实中的家庭远比"配偶 + 子女"复杂：多代同堂、多段婚姻、养子女与继子女、丧偶儿媳/女婿、代位继承、境外亲属、下落不明或已先亡的继承人……任何一个身份判断错误，都会直接改变继承顺序和份额。

**痛点二：资产 ≠ 遗产。** 一套登记在被继承人名下的房产，可能一半是配偶的夫妻共同财产（《民法典》第 1153 条先析产），可能还背着抵押和债务。真正可分配的是**净遗产**，需要经过"总价值 → 析出他人份额 → 扣减债务 → 被继承人遗产"这条链路，而不是把估值直接拿来分。

**痛点三：材料量大且互相交叉冲突。** 户口本、结婚证、判决书、房产证、银行流水、遗嘱的多个版本、死亡证明、赡养证明……几十份材料里，时间对不上、身份有出入、权属有争议、金额不一致、遗嘱前后矛盾、关键证明缺失，是常态。人工逐份比对既慢又容易漏。

> **可引用增强说服力**：最高人民法院及各地法院公布的继承纠纷典型案例中，代位继承认定、丧偶儿媳赡养义务认定、夫妻共同财产析产、遗嘱效力认定等争点反复出现，说明"事实结构化"本身就是专业难点，值得用工具系统化解决。（正式版可补充 2~3 个具名案例。）

## 03｜产品解决方案

EstateGraph Agent 把**一个继承案件转换成「四张图 + 一份报告」**。

- **Family Graph｜继承关系图**
  自动识别被继承人、配偶、子女、父母、（有扶养关系的）继子女、兄弟姐妹、代位继承人等，并对每一条关系保存**关系类型 / 发生时间 / 证据来源 / 可信度**。**[增强中]**：现有系统已有结构化的成员与关系模型（`spouse / son / daughter / stepchild / grandchild / daughter_in_law / sibling …`）及代位继承字段，需要加上"证据来源 + 可信度"维度。

- **Estate Graph｜遗产资产图**
  房产、银行账户、股权、车辆、债权、债务逐项建模，并严格区分**资产总价值 ≠ 被继承人份额 ≠ 净遗产**。**[增强中]**：现有 `Asset` 模型已含类型、估值、夫妻共同财产、可分割性等标记，需扩展债务、抵押与权属份额。

- **Evidence Graph｜证据关系图**
  任何一个结论都能反查到它的**来源材料 + 可信度**，避免大模型凭空断言。**[规划中]**：这是本产品相对 HeirArena 的关键新增能力。

- **Legal Rule Graph｜法律适用图**
  把「人物事实 → 法律身份 → 法条规则」串起来：例如"丧偶儿媳 + 尽主要赡养义务 → 视为第一顺序继承人 → 第 1129 条"。**[已具备]**：规则引擎已把成员事实映射到具体法条编号并输出适用依据。

四张图互相锚定，最终收敛为一份**结构化分析报告**（见 [第 13 节](#13最终输出)）。

## 05｜AI 核心能力

- **Document Intelligence（文档理解）**：从材料中抽取人物、身份、时间、关系、资产、金额、权属、债权债务与遗嘱要点，并为每条事实保留可反查的原文片段。
- **Relationship Reasoning（关系推理）**：构建多代家族关系，识别配偶 / 子女 / 父母 / 继子女 / 兄弟姐妹等，并在子女先于被继承人死亡时**提示代位继承**。**[已具备]** 代位、继子女扶养关系、丧偶儿媳视为第一顺序等判定已在规则引擎中。
- **Timeline Reasoning（时间线推理）**：抽取并排列关键事件（结婚、离婚、出生、收养、立遗嘱、死亡、赡养起止等），因为继承开始时间与顺序高度依赖时间事实（第 1121 条）。
- **Conflict Detection（冲突检测）**：当材料之间事实矛盾（时间对不上、身份有出入、金额不一致、遗嘱版本冲突）时**提示律师核验，绝不自动选边**。
- **Missing Evidence Detection（缺失检测）**：主动列出为支撑某一结论所**缺失的证明材料**（如"主张代位继承但缺子女死亡证明"）。

> **核心原则**：LLM 只负责"理解与提取事实"，一切**影响份额的确定性判断**都交给规则引擎。凡是影响法律计算的关键布尔事实（主要扶养义务、遗弃 / 虐待、扶养关系、被扶养人、夫妻共同财产标记等），都必须带能在原文中反查的短引用，否则保守处理并加入人工确认警告——此约束在现有系统中已实践。

## 06｜AI 工作流

```
材料上传
   ↓  Document Parser（OCR / 版面 / 表格）
   ↓  事实抽取 Agent（人物 / 时间 / 金额 / 权属）
   ↓  人物关系 Agent（家族图 + 代位提示）
   ↓  资产 Agent（总价值 → 份额 → 净遗产）
   ↓  证据冲突 Agent（冲突标记 + 缺失清单）
   ↓  法律 RAG（法条 / 司法解释 / 案例检索）
   ↓  规则计算 Engine（确定性法定份额与分割）
   ↓  Scenario 分割模拟（不同事实假设下的对比）
   ↓  Report Agent（结构化分析报告）
```

**核心原则：LLM 负责理解，规则引擎负责确定性计算。**
两者的分工在现有系统里已通过 "DualPath" 思路落地——模型只输出**符号化事实**，由规则引擎把符号翻译成数值和份额，杜绝"模型直接报一个百分比"。**[已具备]** 编排层为 LangGraph 状态机，每一步可落库、可中断、可重启续跑。

## 07｜精准度目标

| 类别 | 目标 |
| --- | --- |
| 关键确定性任务准确率 | 人物实体、亲属关系、资产金额、数学计算、法条引用需达到**高准确率**（正式版给出量化指标，如 ≥ 95%），错误优先表现为"标记待核"而非"错误结论"。 |
| 核心争议点召回率 | 冲突、缺失、争议点的**召回优先于精确**——宁可多提示律师核验，不可漏掉。 |
| 最终报告 | **必须经律师审核**后方可对外使用；报告以"辅助结论 + 来源 + 待确认项"呈现。 |
| Abstain（弃权） | 证据不足时**不作判断**，明确输出"无法认定 / 需补充材料"。 |
| 可靠性 | 把**"知道自己不知道"**作为可靠性的核心组成部分——系统的价值不只在于答对，更在于诚实标出不确定。 |

## 09｜技术路线

```
Frontend：React / Next.js
   ↓  Case Workspace（案件工作台）
   ↓  Document Layer（MinerU / PaddleOCR）
   ↓  Data Layer（PostgreSQL + Graph DB + Vector DB）
   ↓  AI Layer（LLM + RAG + Agent Workflow）
   ↓  Reasoning Layer（Python Rule Engine）
   ↓  Output（关系图、资产图、证据矩阵、分析报告）
```

**与现有代码的对应关系**：

- **前端**：现为 Vite + React 19 + TypeScript + Tailwind（案件设置向导、关系图 / 份额 / 记录 / 裁决面板、模型选择器）。**[已具备]** 面向本产品可演进为 Case Workspace。
- **AI 层**：LangChain `create_agent()` + LangGraph 状态机 + 多供应商 OpenAI 兼容接入（DeepSeek、通义千问、Kimi、GLM、火山方舟、硅基流动、OpenAI、OpenRouter、Ollama、LM Studio、自定义，可按角色分配模型）。**[已具备]**
- **推理层**：Python 规则引擎（法定份额、析产、代位、折价补偿），含单元测试。**[已具备]**
- **数据层**：现为 SQLite + SQLModel。**[增强中]** 需迁移 / 扩展到 PostgreSQL + 图数据库 + 向量库以支撑图谱与检索。
- **文档层**：**[规划中]** 现仅支持 UTF-8 文本导入，需接入 OCR / 版面 / 表格解析。

## 11｜隐私与安全

继承案件必然涉及**身份、家庭关系、财产、金融、未成年人、健康、私密纠纷**等高度敏感信息。系统必须支持：

- **案件数据隔离**：不同案件 / 客户之间严格隔离；
- **权限控制**：按角色（律师、助理、管理员）最小授权；
- **加密**：传输与存储加密；
- **操作日志**：关键操作可审计；
- **可删除**：支持按案件彻底删除数据；
- **私有化部署**：支持本地 / 内网部署（现有系统已支持接入 Ollama / LM Studio / 本地 Codex 桥接等本机模型，API Key 存本机、不回传浏览器）。**[已具备]** 私有化基础。

> **数据使用红线**：真实案件数据**默认不得用于公共模型训练**。

## 13｜最终输出

产品最终生成一份**《遗产继承案件结构化分析报告》**，包含：

1. 案件基本信息
2. 家族关系图
3. 潜在继承人名单
4. 继承资格分析
5. 资产及债务清单
6. 关键事件时间线
7. 证据矩阵
8. 证据冲突
9. 缺失资料
10. 法律依据及来源
11. 不同情景下的分割结果
12. 需要律师进一步判断的问题

> 报告以"**辅助结论 + 来源 + 可信度 + 待确认项**"的形式组织，每一条结论都能反查到原始材料，供律师核对后交付。

## 14｜产品定位

- **不是 AI 法官**，也不是自动遗产分割器。
- **准确定位**：面向继承律师的复杂案件 **Intelligence Layer（智能层）**。

| 角色 | 负责 |
| --- | --- |
| **AI** | 读材料、找关系、整理资产、查规则、做计算、发现冲突与缺失 |
| **律师** | 判断证据、处理争议、解释法律、给出最终专业意见 |

**最终价值**：把律师的时间从"找资料、画关系、算数字"中解放出来，重新投入到真正需要专业判断的部分。
